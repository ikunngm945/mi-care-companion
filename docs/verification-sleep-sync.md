# 睡眠查询与双向补同步验收

日期：2026-11-13，时区：Asia/Shanghai。

## 睡眠口径

- 无显式时间窗口时，按 `wake_up_time` 的当地日期选择完整会话，午夜醒来属于新一天；不把翌日睡眠的入睡前半段重复计入当天。
- 原生 `duration` 单位为分钟；无分期短睡保留会话和原生总时长，展示“分期不可用”，不补造分期。
- 显式 `start_time` / `end_time`（包括 `24:00`）才裁切会话；无分期且被裁切的时段不能可靠分配总时长，返回 null / “不可用”。
- 跨夜心率和血氧查询从所选会话最早入睡时刻开始，保留前一晚的实测采样。

真实 MCP 的概括和详细查询已逐天核对，包括跨夜完整会话、无分期短睡及显式时间窗口。个人睡眠日期与数值不纳入公开文档；完整证据仅保留本地，不随源码上传。

## 双向补同步机制

助手→运动健康：真实下载原始文件时先清除旧来源，再原子保存文件并记录账号范围与 MAC。文件长度相同也比较完整内容，不漏掉等长更新；直连不发送会消费历史同步状态的文件 ACK。关闭 SPP 后，补同步器才向已鉴权的健康模块发送单文件请求。

健康模块使用当前原生账号、区域和配对设备表确认来源，动态获取 SID；校验 ID、SHA-256、CRC32 和 180000 字节上限。使用运动健康原生 `FitnessDataProcessor.parseAndRecord`，不手写健康记录 SQL。原生 API 自行分派日常与运动文件。

健康账本按账号/区域、设备 SID、MAC、文件 ID、内容哈希区分版本。每次补同步先问健康账本；已成功的同一版本不重复导入。套接字线程只排队并返回 pending，原生导入在独立单线程执行，防止阻塞心跳。真正等待原生回调时保持 pending；回调已结束的异常是 error，不能卡住整个数据库推送。明确不支持的格式跳过并保留原始文件。进程重启后，未确认的旧 pending 可重新走原生幂等 upsert；成功账本继续有效。

运动健康→助手：连接成功、原生近期/历史数据变化和导入批次完成会触发去抖刷新；先用 `VACUUM INTO` 生成一致快照，再分片传输、校验长度与哈希。接收完成后原子替换查询副本，传输中断时保留旧副本。主程序每 30 秒检查补同步，账号范围变化时请求刷新；每 10 分钟的手环直连维持原调度。

来源不明的旧原始文件不自动猜测所属账号。原始运动文件或大文件若原生版本不支持，会保留而不会假报写入成功。MCP 在健康应用离线时继续读取最后一份成功副本；未引入独立的跨账号缓存授权系统。
