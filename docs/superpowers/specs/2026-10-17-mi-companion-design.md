# 小米设备关怀助手：APK 与 AstrBot 初始联动设计

> 历史方案：本文的独立插件与自然日统计已由[官方 HTTP 路由](<../plans/2026-10-17-auto-route-advice.md>)和[睡眠周期设计](<../plans/2026-10-17-sleep-cycle.md>)取代，不代表当前实现。

## 1. 目标和已确认决定

在当前目录交付可安装 APK、源码、构建脚本、必要的 AstrBot 配套插件和中文使用说明。

用户已确认：优先搜索 GitHub，成品不足时自建；采用精简本机采集 / LSPosed Hook；“打开手机”按解锁后持续亮屏计算。连续息屏严格超过 3 小时后保留待触发资格，下一次解锁且连续亮屏严格超过 10 分钟，才汇总小米天气、屏幕使用时长、小米运动健康数据并发给 AstrBot。用户选择 A：中途再次息屏保留资格，但连续使用计时归零，不累计零碎使用。

不是息屏 3 小时立即上报，不使用手机端 OpenAI 接口，不在手机端直接调用消息平台机器人。

## 2. 技术与复用决策

- 数据采集面向 `com.miui.weather2` 和 `com.mi.health`；目录存在不代表数据库可读，必须独立验证 schema、字段、Hook 方法及单位。
- GitHub 调研未核实到完整成品，详见 `docs/research/github-reuse-summary.md` 和 `docs/research/github-health.md`。不搬入整个 HyperCeiler，不依赖未确认的国内版 Health Connect，不增加小米云登录和亲友共享。
- 优先 Android 原生 Java / XML 与标准 HTTP / JSON / SQLite 能力，避免大型界面框架。LSPosed API 仅 compile-time 使用，不把框架实现打包。

## 3. 架构与数据流

1. APK 设置页：本机采集诊断、权限引导、AstrBot 配置、启停监控、“立即测试发送（无时间条件）”按钮、上次事件状态。测试按钮直接采集当前三类数据并提交真实请求，不要求先开启监控，不检查息屏 3 小时、解锁或连续使用 10 分钟；数据缺失时带缺失标记仍可发送。仅要求 AstrBot URL、API key、目标 UMO 等必要配置有效且网络可用，不提供伪造测试成功。
2. 屏幕监控：前台可见监控服务、动态屏幕广播、解锁检查、单调时钟状态机和持久化事件。
3. 采集：原生 UsageStats/UsageEvents 获取屏幕及前台使用情况；LSPosed 模块在天气、健康两个作用域读取其存储 / 模型；如需 root 快照，仅只读访问这两个应用的数据，且不改源文件权限。
4. APK 汇总结构化快照，以持久化 event_id 提交 AstrBot 专用端点。
5. AstrBot 插件校验密钥与目标、去重、调用已配置 LLM、通过 `context.send_message` 向指定会话回复，提供事件处理状态。

仅使用用户自己的设备和指定服务器。APK 无隐蔽运行，无联系人、消息、截图、麦克风采集。常驻通知明确显示监控运行，可随时停止。

## 4. 严格时间状态机

阈值分别为 `10_800_000 ms` 和 `600_000 ms`，比较采用严格 `>`，不是 `>=`。到阈值后的首个调度检查触发，不保证毫秒级定时。锁屏 / 息屏期间 CPU 休眠不要求持续唤醒。

### 状态

- `IDLE`：无待触发资格。
- `OFF`：记录本次连续息屏起点；待触发资格可与该状态并存。
- `ARMED`：至少一段已证实的连续息屏超过 3 小时，尚未成功创建上报事件。
- `USING`：有资格且已解锁、处于 interactive，记录连续使用起点。
- `PENDING`：使用超过 10 分钟已创建本轮持久化事件，等待上传 / 服务端处理。

### 转移

- `SCREEN_OFF`：连续使用计时清零，记录息屏起点；原有资格保留。
- `SCREEN_ON`：先计算刚结束的息屏长度；严格超过 3 小时则设资格。亮屏本身不启动使用计时；如果无锁且已解锁，则立即开始，否则等待 `USER_PRESENT`。
- 解锁并持续亮屏：有资格时进入 `USING`。重复解锁广播不得重置已经开始的计时。
- 使用期间锁定或息屏：计时归零，资格保留；下次解锁重计。定期检查 `isInteractive` 和锁定状态作为广播补充。
- 连续使用严格超过 10 分钟：重新检查屏幕 / 锁状态，再持久化唯一事件并消耗本轮资格，不在每次 tick 重复创建。
- 后续新一段超过 3 小时息屏可以产生下一轮，不与已存在事件混为一轮。

### 重启、进程重建和时钟

- 单次开机内用 `elapsedRealtime`，系统改时间不影响阈值。保存开机标识、状态、计时起点和事件。
- 同次开机进程重建：用可获得的 UsageEvents 补验间隔内的亮屏 / 息屏 / 解锁转换；证据不足则清除“连续使用”计时，不冒充连续使用。只有已证实资格可以保留。
- 设备重启：不跨重启累计连续息屏或使用；已形成的上报事件继续重试，未消耗的已证实资格保留，但使用计时重新开始。
- 首次启用且当前息屏时从启用时开始计时，不伪称知道启用前已息屏多久。
- 用户主动停用监控后停止采集 / 上传；重新启用不追溯停用间隔的连续使用。

## 5. 数据范围与真实性

事件创建时采集快照：

- 天气（用户截图后批准扩展）：首页所选城市缓存的天气描述、气温、体感、高低温、风、气压、湿度、能见度、紫外线、AQI及污染物；有界逐小时/多日/短时降水、日出日落、预警正文与生活指数文案。预报/预警/生活指数保留其各自原时间与单位，未知不可猜，不上传经纬度/城市ID/广告链接。每类限制内尽量覆盖UI，不把raw JSON整包透传。
- 屏幕：设备本地自然日截至采集时刻的屏幕亮屏时长、解锁后使用时长、应用前台使用时长前 10 项；屏幕时长不以各应用时长之和冒充。提供时区、统计区间、权限状态及口径。
- 健康（用户截图后批准扩展）：当天步数、距离、热量、中高强度分钟、站立与目标；各健康指标最近一次记录不限定七天，包括心率/血氧/压力/睡眠分期与统计/体重/血糖/血压，以及已核实有记录的训练负荷/活力/听力。按指标保留真实时间，旧记录明确is_historical，跨日不把旧活动日报当今日。活动次数或单位无法核实时null并说明，不以记录条数猜。每次是当天快照加各指标最近值，不上传整库历史、账号令牌、设备绑定密钥，不凭空生成穿戴设备未采样的指标。

每一类有 `status`（`ok` / `missing` / `stale` / `error`）、`source_package`、`collected_at`、`source_updated_at`（源没有时间时为 null）、`fields` 和不含凭据的 `reason`。缺失为 null，不填 0；明确区分“今日 0 步”和“未读取到步数”。天气和心率超过 6 小时、睡眠结束超过 48 小时标注 stale；这些是提醒标记，不对源数据做补造或医学推断。源时间未知必须明确标注未知。

Hook 仅围绕定位到的相关存储 / 模型，不 Hook 全部网络请求、不截获登录凭据。模块跨进程提交数据时必须验证调用 UID 所属包，并限制数据大小和字段，普通 App 不能伪造更新。模块进程不可读取 API key。

开发时先只读检查版本和 schema，再定位当前版本 Hook 点；若目标存储无法解析，必须将该项标记未完成并说明原因，不能以空壳 APK 宣称已交付全部功能。缓存新鲜度与采集可用性在 UI 可检查；不为刷新天气 / 健康强行打开应用打断用户。

## 6. Android 权限与后台运行

- 必需：网络、前台服务及适用的服务类型声明、通知、使用情况访问授权；需要自启动 / 开机恢复时声明开机广播。
- 用户在 LSPosed 手动启用两个目标作用域；如采用 root 只读快照，由用户显式授权 root。只在目标应用版本验证需要时使用 root。
- 提供通知权限、使用情况访问、电池不限制、自启动的操作引导，不静默关闭系统安全策略。
- Android 16 前台服务启动 / 后台限制、HyperOS 杀后台需要真机验证。不能仅声明一个服务就承诺永不被杀或秒级准时。
- 监控服务不要误用有固定超时的 `dataSync` 类型承担全天监控；采用与本用途匹配且清楚说明的类型，实际清单与 API 36 行为需安装验证。

## 7. AstrBot 接口与配置

APK 配置项：完整 AstrBot 插件事件 URL、插件 API key、目标 UMO；默认只允许 HTTPS，局域网 HTTP 必须用户显式开启。不得使用当前工具连接里配置的 AstrBot 地址 / 凭据替代用户设置。

为避免现成插件版本 / monkey-patch 耦合，优先验证 External Trigger 能否支持完整处理状态与去重；无法满足时提供一个独立配套 AstrBot 插件。最终 APK 只支持文档化的 AstrBot 专用事件协议，不提供通用模型 API 模式。

最小协议：

- `GET <endpoint>/capabilities`：认证后返回 `service: astrbot-mi-companion` 和 `protocol_version: 1`。设置页先校验，不将普通 OpenAI URL 当目标。
- `POST <endpoint>/events`：`Authorization: Bearer <key>`；JSON 含 `protocol_version`、`event_id`、`trigger`（长息屏和连续使用的起止 / 时长）、`collected_at`、`timezone`、`umo`、三类数据。
- `GET <endpoint>/events/<event_id>`：查询 `accepted` / `processing` / `sent` / `failed` / `delivery_unknown`。所有接口均需同样认证。
- 服务端对 event_id 持久化去重，限制 body 128 KiB；拒绝未知版本、无效 UMO、超长字段与未授权目标；不允许远程请求覆盖 LLM provider 或 system prompt。
- 插件 UI 配置独立随机密钥、监听地址 / 端口（默认仅本机，由反向代理对外暴露）、允许投递的 UMO 列表、LLM provider（空则用已配置默认）。不向 APK 暴露模型密钥。
- 插件按目标使用 AstrBot 配置的 provider 生成人性化提醒，明确数据可能过时 / 缺失，手机静置不能推断用户睡眠或健康诊断。结构化数据作为不可信事实上下文，不作为执行指令。
- 必须在 LLM 完成后才调用机器人发送，不直接把原始 JSON 当最终回复。LLM 失败和机器人失败分别记录。

HTTP 2xx 接收不代表最终送达。`sent` 仅表示机器人适配器发送成功返回，不保证用户已阅读。进程崩溃发生在发送已执行但状态未提交之间时记 `delivery_unknown`，不自动重发以避免刷屏；不承诺分布式 exactly-once。

## 8. 重试、安全和可观察性

- API key 用 Android Keystore 加密保存在私有目录，禁备份；UI 遮蔽、日志脱敏，不入源码、不发送给 Hook 宿主。
- HTTP 禁止跨域重定向携带凭据，不关闭 TLS 校验；连接 / 读取超时明确设置。
- 事件提交有网络 / 5xx / 429 错误按退避重试（1、5、15、60 分钟，上限 60 分钟）；401 / 403 暂停自动重试并提示修正配置；其他 4xx 显示协议错误。状态查询不要再次创建事件。
- 手机本地事件最多 100 条；达到上限停止创建新事件并明确告警，不静默丢弃未处理健康事件。已送达详细快照立即清除，摘要超过 7 天清理；未送达事件保留至用户显式删除，避免七天硬清理丢失失败证据。服务端终态删除详细快照、保留去重墓碑。
- 超过 24 小时的未提交事件标记过期，禁止再 POST 原事件；UI 可查看失败原因或显式删除。需要再次测试时用户主动生成新快照、新事件号，不能把旧事件伪装成当前提醒。服务端对已知 ID 可继续返回原处理状态。自动触发入队前配置无效时冻结 UUID、原触发时间及证据，超过 24 小时也不得晚建为当前事件；各类别保留实际采集时间。
- UI 展示当前屏幕状态、资格、连续计时、三类采集结果、最近事件号与阶段。“立即测试发送（无时间条件）”按钮旁常驻说明“会向已配置的 AstrBot 发送真实数据并由机器人回复”；点击即提交，无额外的时间条件或二次确认。每次主动点击产生新的 event_id，`trigger.type` 为 `manual_test`，不消费自动待触发资格，不修改连续使用计时；发送中禁用按钮防止连点，结束后允许再次手动测试。测试请求与自动请求共用采集、鉴权、发送和状态查询路径。测试失败明确显示原因，不显示虚假送达。开发阶段不在未经用户授权时使用真实目标发送测试消息。

## 9. 验收与证据

1. 纯状态机边界测试：恰好 3 小时不获资格，超过才获；恰好 10 分钟不触发，超过才触发；多次息屏重置；锁屏通知不算使用；重复广播不重置；一轮单事件；修改墙钟不影响；重启不累计；失败重试不新建事件。
2. 真机读取：分别显示来自当前天气 / 健康应用的真实字段及时间；与本机应用显示核对单位 / 日期，不在公开日志输出原始私密健康历史。验证屏幕统计口径与权限缺失状态。
3. 构建：干净构建、签名校验、manifest / DEX 检查，生成 APK。无现成完整 SDK 时补齐必需工具，不以编译成功代替安装成功。
4. 安装：在获授权的目标系统验证 APK 可安装 / 启动；安装或启用模块前说明改动，绝不清除原应用数据。
5. 后台与计时：真机测试通知、息屏 / 解锁广播、恢复。用可注入时钟测试长阈值，测试界面或构建不得默认把生产 3 小时 / 10 分钟缩短；未真实等待完整阈值时明确说明。
6. AstrBot：插件单元 / mock 验证鉴权、去重、LLM 后发送、目标白名单、失败阶段；真实服务的完整链路需要用户配置服务地址、密钥、UMO 并授权发送测试消息。缺少这些时仅报告本地验证，不宣称已机器人送达。
7. 无条件手动测试：监控关闭、未满足 3 小时、未满足 10 分钟和健康数据缺失情况下，按钮均能进入同一真实发送路径；只受必要配置 / 网络约束。检查 `manual_test` 标记、每次事件号不同、发送中防连点、自动状态机前后不变、服务端仍先 LLM 后机器人发送。

## 10. 交付边界

交付目录含 APK、源码、可重复构建说明、签名注意事项、AstrBot 插件安装包 / 源码及配置指南、测试结果。首次运行无任何真实 API key；用户自行填写。不能读取的目标字段、未验证的 Android 后台行为、未完成的真实 AstrBot 发送均需列为未完成项，不能以“以后接入”掩盖本需求核心功能缺失。
