## 0.8.0 MCP 按天健康查询

主程序内置只读 MCP Streamable HTTP 端点，端口固定 `17891`，路径 `/mcp`，使用与数据连接相同的 16 位 Token 作为 `Authorization: Bearer <Token>`：

- 本机：`http://127.0.0.1:17891/mcp`
- 局域网/其他设备：`http://<手机局域网IP>:17891/mcp`

提供 10 个独立工具：

- `sleep_summary(date)` / `sleep_detail(date)`
- `heart_rate_summary(date)` / `heart_rate_detail(date)`
- `stress_summary(date)` / `stress_detail(date)`
- `spo2_summary(date)` / `spo2_detail(date)`
- `exercise_records(start_date, end_date)`：返回时间段内的运动摘要和具体 ID；默认当天，范围最多 31 天
- `exercise_detail(id)`：按 `开始时间:结束时间:运动类型` 返回完整摘要、五个心率区段和逐秒明细

`date` 为 `YYYY-MM-DD`，省略为今天，按设备本地时区（当前为 `Asia/Shanghai`）解释。睡眠按醒来日期归档，跨午夜睡眠归到醒来日；`sleep_detail` 返回当天所有睡眠段及每段全部阶段段（起止、阶段、该段心率/血氧范围），一次打包，不是逐段请求。三项指标 detail 固定按 15 分钟桶返回 `HH:mm-HH:mm` 和该桶最小值-最大值；summary 返回当天范围、平均值和采样数。

运动摘要来自数据库 `sport_report`，包含距离、卡路里、平均/最快配速、平均/最高步频、平均步幅、心率区段（热身、燃脂、有氧、无氧、极限）等。`exercise_detail` 的逐秒曲线来自健康应用私有 `sport/p32/<开始时间>_<proto_type>_record` 文件：当前支持本机户外跑（proto 22）的 v5 记录，按原始 1 秒间隔返回心率、步频、步幅、配速、距离增量、卡路里和步数，不做 15 分钟聚合；数据库没有最大步幅字段，最大值从该文件计算。版本不支持、文件缺失或运动类型未知时，仍返回摘要并把明细标为不可用，不伪造曲线。

MCP 查询由健康模块在目标应用进程内只读执行；健康应用未运行时，主程序沿用现有 Root/Shizuku 通道尝试拉起并最多等 15 秒。没有拉起权限或超时会明确返回不可用，不回退 root 读库，也不补 0。MCP 端点监听所有网卡以便局域网客户端访问，必须使用 Token；当前为明文 HTTP，公网使用请自行加 HTTPS 反向代理，不要直接暴露到公网。

AstrBot 的 MCP 配置示例（本机）：

```json
{
  "url": "http://127.0.0.1:17891/mcp",
  "transport": "streamable_http",
  "headers": {"Authorization": "Bearer <主程序显示的 Token>"},
  "timeout": 30
}
```

局域网客户端只把 `127.0.0.1` 换成手机局域网 IP；不要把 Token 写入公开配置或日志。AstrBot 的 MCP 连接会先发一次 `initialize` 做连通性检查，再建立标准 Streamable HTTP 会话；本服务支持该流程。

AstrBot 4.27.4 可在「扩展 → MCP」直接新增上述配置，名称为 `mi_companion`；保存后工具页应出现 10 个工具。该版本自带 MCP 客户端与当前 `mcp` SDK 存在字段名/超时类型兼容问题，本机已按 [验收记录](<docs/verification-mcp.md>) 做三处兼容补丁；升级 AstrBot 后若添加时报 `inputSchema`、`timedelta` 或流数量错误，需要重新应用补丁。

真机验证记录见 [0.8.0 MCP 验收](<docs/verification-mcp.md>)。

## 0.7.0 三 APK 与数据连接

- 安装 `mi-companion-0.8.0.apk`、`mi-companion-weather-0.8.0.apk`、`mi-companion-health-0.8.0.apk`，三者同一签名。主程序包名不变，升级保留原 AstrBot 配置、事件历史和 Key；旧单 APK 的 LSPosed 模块条目会随升级消失。
- 在 LSPosed 中分别启用天气模块（作用域仅 `com.miui.weather2`）和健康模块（作用域仅 `com.mi.health`），然后重启两个目标应用。主程序不再出现在 LSPosed 列表中。
- 主程序“数据连接”区块生成并展示 16 位 Token（大小写字母与数字），默认端口 `17890`，可复制、可重新生成。Token 在本机 no-backup 文件中用 Android Keystore 加密。
- 天气模块在天气应用设置页内容顶部放一个独立按钮“数据连接设置”；点开进入单独的全屏配置页，填端口和 Token 后返回即可。
- 健康模块把健康应用“关于”页内容替换为同一套端口/Token 设置页。
- 后台服务启用时，主程序每小时只把天气/健康数据同步到本机，**不发送给 AstrBot**；发送仍沿用原自动触发条件：连续息屏严格超过 3 小时取得资格，下一次解锁后连续亮屏使用严格超过 10 分钟才发送。每小时同步和发送前才拉起天气/健康（不再因掉线立即拉起）。优先使用 Shizuku，失败时回退 Root；拉起后最多等待 60 秒建立连接。若无法拉起、连接超时或采集不到新数据，发送时使用上一次事件（约 1 小时前）的天气/健康/屏幕数据，并在事件 `trigger.data_fallback` 中明确标注；没有历史数据时发送“不可用”而不是伪造。Root/Shizuku 授权必须由用户在对应管理器中完成，应用不会代替授权；可在“优先使用 Shizuku 拉起”中选择备用通道。
- 两个模块必须填写与主程序完全一致的端口和 Token；保存后立即重连，设置页会显示连接状态、最近心跳和鉴权失败原因。
- 主程序用一条常驻前台服务监听 `127.0.0.1:<端口>`，每 5 秒发送一次 WebSocket ping，10 秒收不到 pong 判定断开；模块按 1、2、4、8、16、30 秒退避重连，连上后立即补发内存中的最新快照。断开期间不排队历史快照。
- 旧版导出的 `content://cn.local.micompanion.snapshots` 已移除；外部应用不能再写入或探测快照。
- 监控开关只控制“是否触发发送”，不再停止数据接收；“停止监控（数据连接保持）”和“停止后台服务（断开数据连接并停止监控）”是两个独立操作。
- 本地构建/测试记录与真机待验收项见[0.7.0 验证](<docs/verification-link.md>)。

### 数据连接安全边界

- 数据连接 WebSocket 服务端只绑定 `127.0.0.1`；MCP 服务为支持局域网客户端监听所有网卡，但必须携带正确 Token，长度、字符集不符直接拒绝。
- 模块配置写在各自目标应用的私有 prefs 中；Token 在本机回环上明文传输，能读设备存储的 root 用户仍可获取。不要把 Token 写进提示词或公开日志。
- 快照仍受 256 KiB、6 字段结构、来源包名和 120 秒周期新鲜度约束；非法快照不落盘。
- 模块不申请额外权限；socket 使用目标应用自身的 `INTERNET` 权限。

## 配置和使用

1. 从 [GitHub Releases](<https://github.com/ikunngm945/mi-care-companion/releases>) 下载三个 0.8.0 APK 并安装：主程序包名 `cn.local.micompanion`，天气模块 `cn.local.micompanion.weather`，健康模块 `cn.local.micompanion.health`。在 LSPosed 中分别启用两个模块，天气模块只勾 `com.miui.weather2`，健康模块只勾 `com.mi.health`；更新模块后重启对应源应用，不清数据。
2. 在助手授权使用情况访问、通知，按需允许 HyperOS 自启动/后台/电池不限制。
3. AstrBot 官方接口填写自己部署的服务地址，例如 `https://astrbot.example.com/api/v1`，域名和端口以实际部署为准。根地址或旧 `/v1` 输入会规范化为 `/api/v1`，不是 OpenAI 模型接口。
4. 填 **AstrBot 官方 API Key**，需要 `chat`、`im` 和 `config` 权限（config范围可能也允许改配置，请妥善保管；本助手只GET读取配置）；不是模型 Key。目标 UMO 在机器人目标会话通过 `/sid` 获取，应含机器人实例ID、消息类型和会话ID。勿只填数字。
5. 默认 HTTPS；勾选后**允许任意地址 HTTP**，不限定局域网，但 Key、天气、健康数据和生成文字均可能被窃听篡改，优先 HTTPS。不会跟随重定向，不关闭证书验证。
6. 点“保存并检查”仅 GET 机器人列表、聊天会话、配置路由及配置档列表，检查权限并显示自动匹配的配置档名称和ID；按完整目标UMO、服务端路由顺序/通配规则匹配，不是仅看机器人ID。无匹配才选择默认配置，读取失败/权限不足/失效配置/会被WebChat通配覆盖时明确失败，不悄悄切换默认人格；不调用模型、不创建聊天、不发消息。服务器可能更新 Key 最近使用时间。进度/结果就在检查按钮下面原地更新，不抢焦点、不自动滚动；异步结束也不会拉回旧阅读位置。列表存在不保证机器人在线。
7. 点“立即测试发送”提交真实数据，先 AI 后发送；无须启用监控或满足时间条件，每次点击是一个新任务。建议确认目标后再点。
8. 自动监控保持：连续息屏**严格超过3小时**取得资格；下一次解锁连续亮屏使用**严格超过10分钟**触发。中途锁定/息屏重计10分钟，资格保留，不累计碎片。不是每日定时发送。停止监控停止自动计时和重试，手动按钮仍有效。

进程中断仅同次开机且有可靠UsageEvents证据才恢复连续时间，否则保守重计；不能保证HyperOS永不杀后台或秒级准时。

## 官方接口的真实边界

- 每任务新建隔离 webchat 会话 `mi-companion-<UUID>`，用户名固定 `mi-companion`，不与其他任务共享聊天历史。生成前重新匹配目标UMO对应配置档，传官方 `config_id`，使用该档人格/模型/工具设置；不修改全局配置。官方chat会为自身WebChat会话登记精确路由，不影响目标会话原路由。这里跟随的是配置档人格，不能保证复制目标会话单独切换的人格或插件注入。GET检查和生成之间服务端配置仍可能被他人改变，不具备原子锁定。
- 新增可编辑多行关怀提示词，保存后生效，“恢复默认提示词”仅修改草稿，仍需保存。空白使用默认，最多4000 Unicode码点。默认分析天气、屏幕、健康并给可行建议，保留服务端人格，整体约300字，不设上限；不按固定码点截断正文。不要把Key填入提示词。
- 每事件冻结创建时提示词；匹配配置ID在生成前保存，已有正文重试若路由指向其他档则暂停，不将旧人格正文补签成新配置。旧0.3 ready正文缺配置来源同样暂停，需用户核对后新建任务。
- 官方API没有单次请求禁工具选项。提示要求只写正文，客户端检测到工具调用即拒绝转发，但不能撤销服务端已经执行的工具。务必在 AstrBot 中按需限制工具与相关插件；关闭 HTTP 流也不代表远端模型/工具已停止。
- 仅提取安全的普通正文，不发送推理、工具结果、附件路径或 `complete.data`。必须收到 `end` 并读到正常EOF，无错误，才发送。
- 生成前持久化 `generating`，发送前持久化 `sending`。官方IM接口没有幂等Key、消息ID或状态查询：响应丢失/进程中断时标 `delivery_unknown`，**绝不自动重发**。中断生成同样不自动重做，防重复费用/副作用。只有未执行模型的接口预检可自动退避重试。
- “查看/重试”只查看本机状态或重试安全的预检，不是远端送达查询；`sent` 仅表示官方发送接口成功返回，不是平台送达或用户已读。确认聊天记录后，才决定是否新建测试任务。
- 原快照超过24小时或时间异常不再请求模型/发送。已发送详情清除，摘要7天后清理；未送达记录不静默清除，最多100条，需用户显式删除。删除不能撤回AstrBot已收到的数据。
- 0.2.0旧插件任务不会自动转投官方地址；旧插件源码仅作为历史实现保留，本版不调用它。不需要安装、配置或重启插件。

## 天气固定精简（0.5.0）

- 继续使用0.5.0的本机固定天气格式器，将天气整理为紧凑中文事实；**精简过程不调用AI**，不增加一次模型请求。天气格式器仅转换生成请求中的 `weather.fields` 为 `weather.facts`；0.6.0随后按下述固定健康/屏幕规则生成事实，原采集快照与本地任务数据不改写。
- 天气码按已核实的小米转换表显示中文，未知码保留原码而不是误报晴；整数UV按原应用固定等级表，小数只保留指数。温度和其他物理量保留源单位，单位未知不猜。
- 已采集的逐小时/逐日记录、预警、生活指数、空气污染物与分钟序列逐条保留；只去重复结构和已知固定技术说明，不额外截断。小时轴仅按已核实的温度预报起点+原 `hour_index` 计算；其他分项原发布时间不同会明确提示，不将它们擅自推导为有效时刻。分钟序列不猜采样间隔。
- 首日不自动称今天，按明确日期及源时区判定采集当天；预报、观测、缓存更新时间分开。缺失不补0，缺测不借上一时段值，不从汇总反造时段数据。
- 原始测量与源文案只作不可信数据；AI仅负责后续建议，不负责重写事实。显示规则证据见 [天气规则](<docs/research/weather-display-rules.md>)、[健康规则与缺测风险](<docs/research/health-display-rules.md>)。

## 健康与屏幕周期事实（0.6.0；0.7.0 增补一周活动、当次睡眠与当天运动）

- **固定规则，无AI预处理。** 健康与屏幕共用一个被冻结的读取周期：`start`为前一次主睡眠结束，`end`为最新Hook实际采集时刻`now`，不是最新睡眠结束，也不是收到缓存时的当前时间。主睡眠按源 `duration >= 180` 分钟判定，需找到最近两次有效、来源结束时刻不晚于采集时刻且结束不同的主睡眠（不以 `isComplete=1` 作为读取门槛）；午睡不切界。仅展示当前（最新）主睡眠的全部来源阶段，最新主睡眠结束后的实测记录仍归入全周期。
- 心率、压力、血氧读取**全周期实测散点**，按周期时区的本地半小时桶显示min/max，首尾裁切；不是从日报48槽反造。样本及相邻睡眠阶段采用 `(start,end]`，边界样本不重复计入；缺测不补0、不沿用上段，单值简写，所有有效桶与当前主睡眠全部阶段保留。本地时间开头只写一次读取区间，不把原始epoch/源元数据交给模型。
- 活动各一行：步数与活动热量在来源内按当地半小时累计，逐槽跨来源取大后求和；热量使用 `BigDecimal` 保留小数。中高强度按真实采样时间并集计分钟。运动报告回查 `start - 7 days`，按 `end_time ∈ (start,end]`归属，保留精确投影去重，跨来源非相同报告重叠时为未知；数据库时间可保留 `dbKeyTime`，不强制等于运动起点。不能用stand、自然日日报或累计运动汇总代替。成功完整运动查询0行才为0次，查询失败/超限为未知，不能把缺失说成0。
- **0.7.0 近 7 天每日活动**：从 `daily_report` 的 `STEP`、`CALORIE`、`MH_STRENGTH` 按本地日一次取近 7 天，逐天列出步数、活动卡路里、中高强度活动分钟，不输出合计；同窗口从 `sport_report` 取运动报告，按天附运动时长与次数。缺失日不补 0，`days_with_data` 标明实际可用天数；日报只取每个本地日的最新一行，避免同一天多条汇总重复相加。
- **0.7.0 睡眠**：当次（最新主睡眠）保留全部阶段、阶段心率/血氧，并汇总总睡眠、清醒、快速眼动、浅睡、深睡；近 7 天其余睡眠只给入睡/醒来、总睡眠和四类分期时长。源记录没有完整四类分期字段时显示“分期时长：暂无数据”，不把缺失写成 0；当次详细数据仍来自 `sleep_segment` 原始阶段，其余来自 `daily_report` 的 `segment_details`。
- **0.7.0 当天运动**：从 `sport_report` 读取当天报告的起止、项目、距离、时长、活动/总卡路里、平均/最快配速、平均/最大心率、步数、平均/最大步频、平均步幅；只保留白名单字段。实测 2026-10-24 10:58 的户外跑步为 221 米、3 分 08 秒、活动卡路里 12 千卡（总 16 千卡）、平均配速 14'10"、平均/最大心率 125/158、286 步、平均/最大步频 111/204、平均步幅 82 厘米。
- **心率、压力、血氧未删除**：仍保留全周期实测分段，并在睡眠摘要之后先给出一行全周期最小～最大范围；当次睡眠阶段内的阶段心率和血氧也继续保留。
- 屏幕统计先冻结健康，再按**完全相同起止**积分亮屏、解锁使用与应用前台时长，展示top10；多查起点前一日用于建立状态，未知初态不补造，UsageEvents缺失会低估。周期不可用或两端无法核对时显示未知，不回退当天。
- Hook主进程每60秒只读刷新（不保证后台永不被杀）；接收端周期滞后**超过120秒**即不可用，恰好120秒仍有效。未来终点、非整数/非法起止或周期超过7天失效；只改变可用状态，不更新`end`补造“截至现在”。
- 有界失败：睡眠只查14天、最多64条；周期最多7天；每类明细最多12000行并加1行sentinel检测超限；当前主睡眠最多512阶段；周期160 KiB、单类别及完整事件各256 KiB（UTF-8）上限。超限明确不可用/停止，不截断事实、不以日报兜底。详见 [周期结构与证据](<docs/research/health-cycle-schema.md>)。
- 官方路由匹配、提示词/Key、自动触发资格及`delivery_unknown`不重发规则**不变**；仍只在后续官方chat调用AI生成建议。0.6.1按用户确认将此前太阳/爱心图片用作自适应桌面图标，兼容圆形和圆角遮罩，原健康采集与发送逻辑不变。

## 数据与隐私

- 不是“当天快照”：模型健康视图使用上述主睡眠周期及同周期屏幕事实，0.7.0 另附一周活动、当次睡眠与其余近 7 天睡眠摘要、当天运动；不传整库历史。旧日报/各指标最近记录仍保留在本机白名单快照用于诊断，但不冒充周期数据，也不将旧体重/血糖称为今天测量；旧快照无有效周期时明确缺失。缺失不填0。
- 天气取首页首选城市的只读缓存，含实况、预报、预警、生活建议，不强制刷新。健康账号不混合。不传账号、设备标识、经纬度或完整原始JSON。自然语言预警正文可能包含地域名称。
- Key用Android Keystore AES/GCM加密在私有不备份目录，Hook宿主读不到；数据连接 Token 同样由主程序加密保存，两个模块则存在各自目标应用的私有 prefs。固定快照和未送达生成正文只在助手私有目录；官方聊天接口会在AstrBot保存聊天，模型供应商也会收到数据，请确认自己的隐私/保留策略。
- 已核实字段和未知单位见 [天气说明](<docs/research/weather-expanded-schema.md>)、[历史日报/最近记录说明](<docs/research/health-expanded-schema.md>)与 [0.6.0周期说明](<docs/research/health-cycle-schema.md>)。历史`daily_activity.activity_count`仍null，不影响新周期独立的`sport_count`；血压等无有效源行仍missing，不造值或医学结论。
